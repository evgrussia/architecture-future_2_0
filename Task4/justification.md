# Обоснование конфигурации Terraform — облачный фундамент «Будущее 2.0»

Конфигурация реализует **этап 1 роадмапа** ([Task3](../Task3/tech-radar-and-roadmap.md)) — облачный фундамент для платформы данных: сеть, NAT, security group, виртуальные машины и диски в Yandex Cloud.

Диаграмма автоматизации развёртывания (какие компоненты управляются Terraform, а какие создаются вручную) — в файле [`diagram.png`](./diagram.png).

## 1. Выбор провайдера и подхода

- **Yandex Cloud (IaaS).** Соответствует требованиям проекта по работе с медицинскими и финансовыми данными в РФ (резидентность данных, требования регуляторов) и понятийному аппарату задания (VM, Disk, Network, NAT).
- **Декларативный подход (Terraform/HCL).** Мы описываем *желаемое состояние* инфраструктуры, а Terraform сам вычисляет, что создать/изменить/удалить. Это исключает ручные клики в консоли, человеческие ошибки и «дрейф» конфигурации, а также даёт предсказуемый `plan` перед любым изменением.

## 2. Структура проекта

| Файл | Назначение |
|---|---|
| `versions.tf` | Пины версий Terraform и провайдера — воспроизводимость между запусками и членами команды |
| `variables.tf` | Объявление переменных с типами, описаниями и значениями по умолчанию |
| `main.tf` | Описание инфраструктуры (сеть, NAT, SG, ВМ, диски) |
| `outputs.tf` | Вывод ключевых параметров (IP, ID ресурсов, готовая SSH-команда) |
| `terraform.tfvars` | Конкретные значения переменных для окружения |
| `diagram.png` | Диаграмма автоматизации развёртывания (Terraform vs ручное) |

## 3. Обоснование ресурсов и параметров

### 3.1. Сеть (Network)
- **Одна VPC-сеть** `future-2-0-net` как изолированный сетевой периметр фундамента.
- **Две подсети**:
  - *Публичная* (`10.10.1.0/24`) — только для bastion/точки входа.
  - *Приватная* (`10.10.2.0/24`) — узлы платформы данных. Они **не имеют публичных IP**, что снижает поверхность атаки — критично для мед/фин данных.
- Разделение `/24` на подсеть даёт 251 доступный адрес — с запасом под горизонтальное масштабирование узлов.

### 3.2. NAT
- **NAT-шлюз** (`shared_egress_gateway`) + **таблица маршрутизации** с маршрутом `0.0.0.0/0 → NAT`, привязанная к приватной подсети.
- **Зачем:** узлам платформы нужен исходящий доступ в интернет (обновления пакетов, скачивание образов, обращение к управляемым сервисам), но **входящие подключения из интернета к ним запрещены**. NAT обеспечивает «выход без входа» — стандартная безопасная схема для приватного слоя.

### 3.3. Security Group
- Входящий **SSH (22)** — только с `allowed_ssh_cidr` (по умолчанию открыт, в проде сужается до офисного IP/32).
- **Любой трафик внутри самой группы** (`self_security_group`) — для межузлового взаимодействия компонентов платформы.
- **Исходящий** — разрешён весь (работает совместно с NAT для приватных узлов).

### 3.4. Виртуальные машины (VM)
- **Bastion** — `2 vCPU / 2 ГБ` достаточно для роли шлюза доступа (он не несёт нагрузки, только проксирует SSH). Публичный IP (`nat = true`).
- **Узлы платформы данных** — `app_node_count = 2` по `2 vCPU / 4 ГБ`. Количество узлов меняется **одной переменной** — это и есть масштабируемость IaC: `app_node_count = 5` → пять узлов одним `apply`.
- **`platform_id = standard-v3`** — актуальное поколение платформы с лучшим соотношением цена/производительность.
- **`core_fraction = 20`** — гарантированная доля vCPU 20% для экономии в тестовой среде; для продакшена выставляется `100`. Параметр вынесен в переменную, чтобы менять без правки кода.

### 3.5. Диски (Disk)
- **Загрузочные диски** — `network-ssd`, 20 ГБ: хватает под ОС и системное ПО, SSD даёт быстрый старт.
- **Дополнительные диски данных** — отдельный `network-ssd` 50 ГБ на каждый узел, подключается как `secondary_disk`.
- **Зачем отдельный диск данных:** разделение ОС и данных позволяет независимо менять размер, делать снапшоты и переносить данные без переустановки ОС — это упрощает эксплуатацию платформы данных.

## 4. Что управляется Terraform, а что вручную

**Вручную (предпосылки, см. `diagram.png`):** аккаунт и биллинг, облако (`cloud_id`), каталог (`folder_id`), сервисный аккаунт с ролями и JSON-ключ, генерация SSH-ключа. Эти сущности либо требуют действий человека/организации, либо являются «корнем доверия» и намеренно не автоматизируются. Установка прикладного ПО внутри ВМ выполняется отдельно (Ansible/cloud-init) и вынесена за рамки IaaS-слоя.

**Terraform:** сеть, подсети, NAT-шлюз, таблица маршрутизации, security group, образ (data source), bastion и его диск, узлы платформы, их загрузочные и дополнительные диски.

## 5. Как IaC обеспечивает воспроизводимость и масштабируемость

- **Воспроизводимость.** Один и тот же код + `terraform.tfvars` дают идентичную инфраструктуру в любом каталоге/окружении (dev/stage/prod). Версии провайдера запинены (`versions.tf`), состояние фиксируется в state-файле, `plan` показывает изменения до применения. Среды доменов из [Task2](../Task2/domains-and-data-flows.md) поднимаются по единому шаблону.
- **Масштабируемость.** Горизонтальное масштабирование — изменением `app_node_count`; вертикальное — переменными `app_cores`/`app_memory_gb`/дисков. Новый домен (фарма, электроника из роадмапа) получает свою среду переиспользованием этой же конфигурации с другими `tfvars`, без ручной сборки.
- **Управляемость.** Вся инфраструктура — в Git: код-ревью, история изменений, откат к предыдущему состоянию. Это снижает операционные риски и ускоряет вывод изменений (поддерживает цели time-to-market и надёжности из Task1/Task3).

## 6. Запуск и тестирование (`init` / `plan` / `apply`)

Предпосылки (выполняются вручную один раз): аккаунт Yandex Cloud с биллингом; сервисный аккаунт + роли (`editor` или `vpc.admin` + `compute.admin`), скачанный JSON-ключ рядом как `key.json`; SSH-ключ (`ssh-keygen -t ed25519 -f ~/.ssh/id_rsa`); заполненные реальные значения в `terraform.tfvars` (`cloud_id`, `folder_id`, пути к ключам).

```bash
cd Task4
terraform init      # инициализация провайдера yandex-cloud
terraform fmt       # (опц.) форматирование
terraform validate  # проверка синтаксиса и связности
terraform plan      # предпросмотр изменений
terraform apply     # создание инфраструктуры (подтвердить: yes)
terraform output    # просмотр ключевых параметров (IP, ID ресурсов)
```

После успешного `apply` сделайте **скриншот** строки `Apply complete! Resources: N added` и сохраните его как `Task4/apply-result.png` — он включается в пул-реквест согласно требованию задания. Удаление инфраструктуры после проверки: `terraform destroy`.
